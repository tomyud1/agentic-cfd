GPU versus CPU pressure solver: DFG 3D-1Z cylinder (Re = 20)

Summary ✓ Fair comparison, same answer

Question. How much faster does this machine solve this problem when the pressure equation is solved on the GPU (RTX 4070, through the OGL plugin) instead of the CPU, and from which mesh size does the GPU pay off?

The GPU is faster per iteration from about \(2.0\) million cells: on the largest mesh (4,752,000 cells) one iteration takes \(3.80\,\mathrm{s}\) on the best CPU setup (GAMG DIC-GS, 8 ranks) and \(3.37\,\mathrm{s}\) with the pressure solved on the GPU (8 ranks), a factor \(1.13\); the pressure solve alone takes \(1.44\) against \(0.87\,\mathrm{s}\) (factor \(1.65\)). Both give the same converged forces.

Key findings

  • Tuning mattered more than hardware. With OGL's default multigrid the GPU needed \(132\) CG iterations per pressure solve (GAMG: \(9.4\)): its coarsest level keeps 64000 rows and is 'solved' by one Jacobi sweep. A small coarsest level solved by CG and two smoothing sweeps brought it to about \(16\); building that deeper hierarchy then cost more than the solve, until the preconditioner was reused for 20 solves (the pressure matrix changes slowly between SIMPLE iterations).
  • Size dependence. Speed-up per iteration G16 \(0.23\), L3 \(0.55\), G36 \(0.90\), L4 \(1.03\), G60 \(1.13\); pressure solve alone G16 \(0.08\), L3 \(0.19\), G36 \(0.69\), L4 \(1.11\), G60 \(1.65\). Both sides change with size, in opposite directions. Time of one pressure solve per million cells: CPU G16 \(0.081\), L3 \(0.081\), G36 \(0.153\), L4 \(0.226\), G60 \(0.302\) \(\mathrm{s}\), GPU G16 \(1.084\), L3 \(0.426\), G36 \(0.221\), L4 \(0.203\), G60 \(0.183\) \(\mathrm{s}\). The GPU gets cheaper per cell because its fixed costs per solve (kernel launches, transfers, the coarse levels) are spread over more cells and its many cores fill up. The CPU gets dearer per cell, \(3.7\times\) from its cheapest to the largest mesh; GAMG also needs a few more cycles on larger meshes (G16 \(2.8\), L3 \(6.4\), G36 \(4.6\), L4 \(5.0\), G60 \(5.7\)), and the rest is consistent with the data leaving the CPU's 96 MB L3 cache (not measured directly).
  • Amdahl's limit. On the CPU the pressure solve is G16 \(35\,\%\), L3 \(28\,\%\), G36 \(30\,\%\), L4 \(32\,\%\), G60 \(36\,\%\) of an iteration (profiling). Even an infinitely fast pressure solver could speed an iteration up by at most G16 \(1.55\times\), L3 \(1.39\times\), G36 \(1.42\times\), L4 \(1.46\times\), G60 \(1.57\times\): momentum, assembly and the force output stay on the CPU.
  • Rank count. 8 ranks (one per physical core) were fastest for both the CPU and the GPU runs on every mesh. Hyper-threads add MPI traffic but no memory bandwidth; for the GPU runs, more ranks speed up the CPU part but every rank's matrix has to travel to the one GPU through host memory (L4: Figure 2).
  • Same answer. The converged forces of the GPU and CPU runs agree to \(6.7 \times 10^{-10}\) (drag) and \(9.8 \times 10^{-10}\) (lift), far below the mesh error; a partial linear solve changes the path, not the steady state.
LimitationOne consumer GPU (RTX 4070): fast memory but slow double-precision arithmetic; a data-centre GPU would do better. Ubuntu's Open MPI is not CUDA-aware, so every pressure matrix and solution passes through host memory (forceHostBuffer).
LimitationOnly the pressure linear solve runs on the GPU; OGL cannot move assembly or the momentum equations there.
LimitationTuning was time-boxed (24 configurations on one mesh, 4 ranks); part of it ran next to other runs (marked), which inflates its times but not its iteration counts. A better GPU preconditioner may exist.
LimitationTiming runs are 30 iterations from rest; converged runs were compared on L3 and L4.
LimitationOGL is a development version (commit 7c3ced4), tested by its authors on OpenFOAM v2512, run here on v2606.
RecommendationBelow about \(2.0\) million cells keep GAMG (DIC-Gauss-Seidel smoother, 8 ranks) on the CPU; above it the tuned GPU solver is worth switching on for long runs, but expect about \(11\,\%\) less time per iteration at 4.8 million cells, not a multiple. A real gain needs either a GPU with fast double precision, a CUDA-aware MPI (no host copies), or a solver that also moves momentum and assembly to the GPU.

1 What is compared

Both sides solve the same steady problem with the same OpenFOAM solver (simpleFoam, SIMPLEC) on the same meshes, with the same schemes, tolerances, function objects and start field. Only the pressure linear solver changes: GAMG on the CPU cores, or OGL's Ginkgo CG with a multigrid preconditioner on the GPU. In each SIMPLE iteration OpenFOAM assembles the pressure equation on the CPU; with OGL the matrix is then sent to the GPU, solved there and the solution sent back. Meshes: the O-grid family of the main report (L3, L4) plus three extra sizes of the same blocking (G16, G36, G60), 90,112 to 4,752,000 cells.

Rules for a fair comparison

  • CPU baseline = the fastest measured GAMG setup per mesh: two smoothers (Gauss-Seidel, DIC-Gauss-Seidel) and 8 or 16 ranks on every mesh, 4 to 16 ranks on L4; not PCG on one core. Chosen per mesh: G16: GAMG DIC-GS, 8 ranks, L3: GAMG GS, 8 ranks, G36: GAMG DIC-GS, 8 ranks, L4: GAMG DIC-GS, 8 ranks, G60: GAMG DIC-GS, 8 ranks.
  • Same tolerances on both sides: each pressure solve to \(\mathrm{relTol} = 0.05\) of its initial residual, OpenFOAM's normalised residual (OGL computes the same norm), absolute tolerance \(1 \times 10^{-12}\) (never reached).
  • Same work: 30 SIMPLE iterations from the same start field (rest); time per iteration over iterations 6 to 29, so one-off costs (GAMG agglomeration, CUDA start-up, the final write) are excluded on both sides.
  • Converged comparison runs start from the same converged coarser-mesh field and stop on the same residual rule.
  • Timing runs one at a time, nothing else running; repeats on the largest mesh.
  • Clock: rank 0's ExecutionTime (0.01 s resolution) where it equals wall time (checked against OpenFOAM's high-resolution profiled wall time of the loop: at least 70 % of it, the rest being one-off costs); otherwise the profiled wall time of the whole loop / 30, marked * in the tables (1 run(s): 16 ranks on the smallest mesh, where MPI lets rank 0 sleep). The log's ClockTime has 1 s resolution (Insights).

2 Method

Three kinds of runs: short tuning runs of the GPU solver on one mesh, fixed-length timing runs on five mesh sizes, and converged runs on two meshes to check that the answer is the same.

M1
Timing protocol: 30 SIMPLE iterations from rest; time per iteration over iterations 6 to 29
Why this choice
A converged run on every mesh would cost hours; the cost per iteration is what a solver change affects, and the converged runs (L3, L4) show that both sides need the same number of iterations.
Alternatives
Converged runs on every size (5-10 times the compute); single-solve benchmarks outside OpenFOAM (would miss the transfer and assembly costs).
M2
Time split by OpenFOAM's built-in profiling (pressure solve, momentum solve, function objects, rest) and OGL's own per-solve timings (matrix transfer, preconditioner set-up, GPU solve, copy back)
Why this choice
Profiling measures both sides identically; OGL's verbose output splits the GPU path further.
Alternatives
nsys/nvprof GPU profiles (not available in WSL here).
M3
GPU solver: Ginkgo CG, multigrid preconditioner (PGM aggregation), coarsest level at most 1000 rows solved by 20 CG iterations, 2 Jacobi smoothing sweeps, preconditioner reused for 20 solves, adaptMinIter off, scaling -1, forceHostBuffer true
Why this choice
The fastest of the 24 configurations tried on the 1-million-cell mesh (Results); OGL's defaults needed many times more iterations than GAMG.
Alternatives
Block Jacobi, ISAI, IC preconditioners (hundreds of iterations, tried); SSOR smoother (fewer iterations, slower); Csr format; more smoothing sweeps (tried).
M4
GPU rank count: the CPU part runs on N MPI ranks, all sending their rows to the one GPU (ranksPerGPU N); N = 2, 4, 8, 16 tested on L4
Why this choice
More ranks speed up assembly and momentum, but each extra rank adds a matrix transfer and gather.
Alternatives
One rank per GPU (OGL refuses serial runs; at least 2 ranks).
M5
Same-answer test: converged runs on L3 and L4, CPU and GPU, from the same start field; tolerance \(|\Delta c_D| \le 1 \times 10^{-4}\), \(|\Delta c_L| \le 1 \times 10^{-5}\), fixed before the runs
Why this choice
Ten times below the mesh uncertainty (GCI) of each number on L4: a GPU solve that changed the answer by more would matter.
Alternatives
Comparing fields after a fixed number of iterations (partial solves take different paths, so unconverged states differ even when both are right).

Performance and GPU entries of the case's live insight log: what limited speed, what helped, what to try next. Each entry shows its problem; open it for the diagnosis, the fix and the lesson.

gpu logged 2026-11-11 17:27
environment.md lists the GPU multigrid options to explore as MaxLevels, MinCoarseRows and ZeroGuess. The OGL source (include/OGL/Preconditioner/Multigrid.hpp, CoarseSolver.cpp) reads them in lower camel case (maxLevels, minCoarseRows, smoother, maxIterSmoother, coarseSolver, maxIterCoarse, cycle, reuseHierarchy) and only from a preconditioner SUB-dictionary; there is no ZeroGuess option. Written as top-level keys they would be ignored silently.
Diagnosis
The option names in the guidance were guessed, not read from the plugin. OGL looks the preconditioner options up in the dictionary of the preconditioner entry (preconditioner { preconditioner Multigrid; minCoarseRows 1000; ... }). Its defaults are weak for a large 3D problem: the coarsest level keeps 64000 rows and is 'solved' by ONE Jacobi sweep (coarseSolver Jacobi, maxIterCoarse 1), with one Jacobi smoothing sweep per level.
Fix
Read the option names and defaults from ~/src/OGL before tuning; write them in a preconditioner sub-dictionary (run.py CONFIGS).
Lesson
Read the plugin's source for option names and defaults before tuning; a misspelt option in an OpenFOAM dictionary is ignored without a warning.
Guideline
environment.md, OGL section: replace 'MaxLevels, MinCoarseRows, ZeroGuess' by the real names, show the sub-dictionary form and the defaults (minCoarseRows 64000, coarse solver = 1 Jacobi sweep).
performance logged 2026-11-11 17:33
The study needs the pressure-solve time of CPU runs, but GAMG prints no timings and cfdlib.perf only counts iterations. OpenFOAM's built-in profiling (controlDict: profiling { active true; }) writes /uniform/profiling with the wall time and call count of every section: fvMatrix::solve.p, fvMatrix::solve.U, each function object, for CPU and GPU runs alike (processor0/... in parallel runs).
Diagnosis
Profiling is off by default and not mentioned in the guidelines. One quirk: its GAMG entry 'lduMatrix::solver.coarsestLevelCorr' reports almost the whole pressure solve (a nesting artefact), so only fvMatrix::solve.p is used.
Fix
Profiling on in every run of this case (an output decision); run.py reads the totals per section from processor0.
Lesson
Before writing log parsers for timings, check what the solver can already measure about itself.
Guideline
SKILL.md performance section: switch on controlDict profiling for any performance study and read fvMatrix::solve.; cfdlib.perf.summarize could parse uniform/profiling itself.
gpu logged 2026-11-11 17:33
OGL's stopping criterion has adaptMinIter (default true): every pressure solve must do at least 0.6 times the iterations of the previous one (log: 'Creating stopping criterion with minIter 421 frequency 6'), and the residual is checked only every few iterations. In a steady SIMPLE run with partial solves (relTol 0.05) this can force far more iterations than the tolerance needs.
Diagnosis
Measured on the 1-million-cell mesh (4 ranks): with OGL's default multigrid, switching adaptMinIter off cut the CG iterations per pressure solve from 132 to 97. With the tuned preconditioner the effect is small (16 with it, 15 without), because the iteration count no longer varies much between solves.
Fix
adaptMinIter false in every tuned GPU configuration (run.py _gpu_mg).
Lesson
Library defaults tuned for transient runs with full solves can waste work in steady runs with partial solves.
Guideline
environment.md OGL section: mention adaptMinIter (default on) and set it off for partial (relTol) solves.
performance logged 2026-11-11 17:33
The forces function object costs about 6 % of each iteration on the 2.43 million cell mesh (two calls, cylinder and walls, 0.064 s each per iteration on 16 ranks; profiling): it evaluates the stress tensor on the whole mesh, not only on the patch.
Diagnosis
forces builds devRhoReff (needs grad U everywhere) every call; at 2.4 million cells that is not free.
Fix
Kept every iteration (identical on CPU and GPU runs, so the comparison stays fair) and reported as part of the time outside the pressure solve.
Lesson
Every-iteration function objects are a measurable cost on large meshes and dilute any linear-solver speed-up.
Guideline
For long steady runs, evaluate forces every few iterations (executeInterval) once the stopping rule allows it.
performance logged 2026-11-11 17:58
OpenFOAM's per-iteration ClockTime in the log, which run.py and case 4 (_loop_us) use for time per iteration, is printed in whole seconds: on a 0.05 s iteration it is useless, on a 0.6 s one it carries a 5-10 % error over 20 iterations. The timeInfo function object's clockTime column has the same 1 s resolution.
Diagnosis
Time::elapsedClockTime returns whole seconds. ExecutionTime (CPU time of rank 0, 0.01 s resolution) looked like wall time on the first checks, but on the 90 thousand cell mesh with 16 ranks it was half the wall time (0.020 against 0.039 s per iteration): with 16 ranks on 16 hardware threads, MPI yields the core instead of busy-waiting. That made 16 ranks look fastest on the small meshes. Profiling's totals (time.run()) are high-resolution wall times.
Fix
Time per iteration = profiled wall time of the iteration loop divided by the iteration count, on both sides (includes the first iteration's one-off costs, the same for every run of a mesh up to the GPU's CUDA start-up).
Lesson
Check the resolution AND the meaning (CPU or wall) of a clock before timing with it, on the smallest case too.
Guideline
cfdlib.perf: compute loop time from ExecutionTime differences (or profiling), never from ClockTime; say in SKILL.md that ClockTime has 1 s resolution.
gpu logged 2026-11-11 18:06
After the coarse-level fix (CG coarse solve, coarsest level at most 1000 rows) the GPU needed only 15 CG iterations per pressure solve, but the multigrid set-up then cost about 0.9 s per solve on 1 million cells, several times the solve itself, so the GPU was still slower than GAMG.
Diagnosis
OGL rebuilds the multigrid hierarchy (PGM aggregation on the GPU) for every solve by default; a deeper hierarchy costs more to build.
Fix
Reuse the preconditioner for 20 solves (preconditioner { caching 20; }): the pressure matrix changes slowly between SIMPLE iterations, so the stale preconditioner costs about 1-4 extra CG iterations and saves the set-up. reuseHierarchy (recompute only the coarse matrices) helped less.
Lesson
On the GPU, preconditioner set-up can dominate; amortise it over solves.
Guideline
environment.md OGL section: start GPU tuning from minCoarseRows ~1000, coarseSolver CG, maxIterSmoother 2, caching 20, adaptMinIter off (the settings found here), not from the defaults.
performance logged 2026-11-11 18:39
The CPU baseline is not 'GAMG on all cores': on this steady 3D case GAMG with the DIC-Gauss-Seidel smoother needs 5 instead of 13 iterations per pressure solve and is about 6 % faster per iteration than with Gauss-Seidel, and 8 ranks beat 16 on every mesh from 0.3 to 4.75 million cells (L4: 1.72 s per iteration on 8 ranks, 1.90 on 16). Case 4 (2D, transient) had found 16 ranks fastest.
Diagnosis
A steady 3D SIMPLE iteration is memory-bandwidth bound; hyper-threads add MPI traffic and halo work without adding bandwidth. DIC smoothing does more per sweep but converges GAMG in fewer cycles.
Fix
The study's CPU baseline is the fastest of GAMG GS / GAMG DIC-GS on 8 or 16 ranks per mesh (4-16 on L4).
Lesson
'Best CPU setup' must be measured for each case; smoother and rank count both matter by 5-15 %.
Guideline
primer, parallel section: add this case's numbers (8 ranks best for steady 3D, DIC-GS smoother) next to case 4's.
gpu logged 2026-11-11 19:15
Even fully tuned, the GPU only breaks even at about 2 million cells and saves about 11 % of the time per SIMPLE iteration at 4.75 million cells (a factor 1.13), although its pressure solve there is 1.65 times faster than the best GAMG; on a converged L4 run both took about 11.5 minutes.
Diagnosis
Three limits stack up. (1) Amdahl: the pressure solve is only about a third of a steady SIMPLE iteration (momentum, assembly and the force output stay on the CPU), so even an infinitely fast solver gives at most about 1.5 times. (2) Each solve pays a fixed host path: the ranks' matrices are gathered and copied through host memory (no CUDA-aware MPI), tens of milliseconds outside OGL's own timers. (3) The consumer GPU's double precision is slow, so CG with multigrid needs 3 times the iterations of GAMG with DIC smoothing and gains only from memory bandwidth.
Fix
Reported as the answer: break-even and gains measured, with the same converged forces on both sides.
Lesson
For steady incompressible OpenFOAM runs, offloading only the pressure solve cannot give more than the pressure share allows; measure that share first (profiling) before investing in GPU tuning.
Guideline
SKILL.md performance study: start by measuring the pressure share with profiling and state the Amdahl bound; it sets expectations before any GPU run.
